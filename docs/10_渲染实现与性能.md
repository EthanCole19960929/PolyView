# 10 渲染实现与性能

> 作者：program　日期：2026-10-23
> 本文按仓库里的真实代码写（`SceneRenderer.cs`、`ModelViewport*.cs`、`Core/Gizmo.cs`、`MeshData.cs`），实测数字全部引自 [04_渲染原理与优化.md](04_渲染原理与优化.md) §5；其余内存数字是**按代码里的数据格式用公式推算的**，标了「推算」，没有实测。

## 1. 一句话回答

PolyView 用的是**光栅化**：Direct3D 11 在显卡上把每个三角形投影到屏幕、逐像素算颜色，原理和 Blender 视口里的 **Workbench（实体模式）/ Eevee（材质预览、渲染预览）** 是同一类，但比它们简单得多（没有阴影、环境光遮蔽、反射、环境贴图、PBR 材质）；和 Blender 的 **Cycles（路径追踪，算光线反弹）** 不是一回事。它**只在画面需要变化时才画**（按需渲染），不动鼠标时 GPU 基本是空闲的。内存的大头是模型本身：每个顶点 36 字节、每个三角形 12 字节索引，而且 CPU 和显存里**各存一份**；100 万三角形的 STL 实测私有内存约 615 MB，在普通电脑上没问题，500 万三角形开始吃力。

## 2. 每一帧的渲染流程

### 2.1 什么时候画一帧（按需渲染）

- `ModelViewport` 挂在 WPF 的 `CompositionTarget.Rendering` 上（跟显示器刷新走，60 Hz 屏就是每秒最多 60 次回调）。
- 每次回调先看 `_dirty`：**没有变化就直接 return，什么都不画**。转视角、选中、移动物体、加灯、改着色模式、改窗口大小等都会调用 `Invalidate()` 把 `_dirty` 设成 true。
- 启动、改尺寸、改 DPI、显卡设备恢复时会连续画几帧（`_warmupFrames`），保证第一帧一定显示出来（`cc62422` 修的启动灰屏就是这个）。
- 窗口还没有尺寸（宽或高 < 1）时不画，记下 `_resizePending`，等有尺寸了再画。

### 2.2 一帧里依次做什么（`RenderFrame` → `SceneRenderer.Render`）

| 步骤 | 做什么 | 代码 |
| --- | --- | --- |
| 0 | CPU 准备：更新变换手柄、坐标轴小球、灯光常量缓冲（最多 16 盏灯） | `UpdateGizmo` / `UpdateNavGizmo` / `UpdateLights` |
| 1 | **清屏**：颜色清成深灰 (0.11, 0.12, 0.14)，深度清成 1 | `ClearRenderTargetView` / `ClearDepthStencilView` |
| 2 | **模型**：每个可见对象绑定一次顶点/索引缓冲，按材质分段（MeshPart）逐段 `DrawIndexed`；隐藏的部件跳过；双面材质用不剔除背面的光栅状态；线框模式换成线框光栅状态 | `Render` 里的 for 循环 |
| 3 | **地面网格**：在模型之后画，线段（LineList），深度测试开、不写深度，所以被模型挡住的部分不显示；不受光照（Unlit） | `ShowGrid` 段 |
| 4 | **灯光图标**：灯在视图里的线条图标 | `DrawLightIcons` |
| 5 | **选中描边**：① 把选中的物体（或选中节点的部件）画进一张单通道遮罩纹理（R8，选中处=1）；② 用一个全屏三角形跑边缘检测：自己不在遮罩里、但周围 5×5 像素内有遮罩的像素，涂成 Blender 橙 (1.0, 0.627, 0.157)，半透明混合叠到画面上 | `DrawOutline`、`PSMask`、`PSOutline` |
| 6 | **变换手柄**：移动/旋转/缩放手柄（线 + 三角形，启动时由 `Gizmo.Build` 一次性生成一个顶点缓冲），不受光照，悬停时往黄色高亮 | `DrawGizmo` |
| 7 | `Flush()` 把命令交给显卡 | |
| 8 | **交给 WPF 显示**：D3D11 的颜色纹理创建时带 `Shared` 标志，D3D9Ex 用同一个共享句柄打开它（`A8R8G8B8`），作为 `D3DImage` 的后台缓冲；每帧只需 `AddDirtyRect` 通知 WPF「这块内容更新了」，**不用把像素拷回 CPU** | `ResizeSurface`、`RenderTick` |

右上角坐标轴小球（`ModelViewport.NavGizmo.cs`）和着色模式按钮、左侧工具栏是 WPF 控件，叠在 3D 画面上面，由 WPF 自己画。

### 2.3 着色器

所有 HLSL 写在 `SceneRenderer.cs` 的字符串里，启动时用 `d3dcompiler_47.dll` 运行时编译。只有一个通用顶点着色器 `VSMain`（乘 WorldViewProj，输出法线、UV、顶点色、世界坐标）和一个通用像素着色器 `PSMain`，用常量里的 `Unlit` 和 `Ambient.w` 区分模式；另外两个小着色器 `PSMask`、`PSOutline` 给描边用。

## 3. 着色模式和光照公式

`Ambient.w` 传模式码：1 = 渲染，2 = 实体，3 = 材质预览（`ModelViewport.Shading.cs` 的 `ShadingCode`）。

| 模式 | 做什么 |
| --- | --- |
| 线框 | 换成线框光栅状态画三角形边，其余同实体（模式码 2） |
| 实体（默认） | **不用贴图**，只用顶点色；光照 = 跟随相机的主光 + 半球环境光（见下） |
| 材质预览 | 同实体的光照，但颜色 = 基础颜色贴图 × 顶点色 |
| 渲染 | 贴图 × 顶点色，用**场景里的灯光和 World 环境色**照明 |

**实体 / 材质预览的光照**（不看场景灯光，任何角度正面都亮）：

- 主光方向跟着相机，在相机右上方：`L = normalize(-前方 + 0.45×右 + 0.75×上)`。
- `颜色 = 基色 × (半球环境 + 0.75 × max(0, N·L))`，半球环境按法线朝上程度在 0.32（朝下）到 0.55（朝上）之间插值。
- 背面朝向相机时法线取反，所以双面薄片两面都有光。

**渲染模式的光照**（docs/07 §4.2）：

- 漫反射是 **Lambert**（`max(0, N·L)`），加一点 **Blinn-Phong 高光**：`pow(max(0, N·H), 48) × 0.15`，高光强度是写死的，不看材质。
- 点光 / 聚光 / 面光：**平方反比衰减** `1/d²`；如果灯有 Range，再乘一个平滑淡出 `(1-(d/Range)^4)²`。
- 聚光：内外锥之间 `smoothstep` 过渡。面光：目前按「朝一个方向的点光」近似，再乘 `max(0, 面朝向·光方向)`，没有真正的面积积分。
- 日光：方向光，不衰减。
- 环境：`基色 × World 颜色 × 强度`（均匀环境光，不是 HDRI）。
- 单位按 Blender：点/聚/面光的 Power 是 W，日光 Strength 是 W/m²。换算在 `ModelViewport.Lights.cs`：点/聚光 `I = P / (4π)`，面光 `I0 = P / π`，Lambert BRDF 乘 `1/π`，日光直接用 Strength。
- 最后用 `1 - exp(-sum)` 做柔和曝光压缩，让 1000 W 的灯不至于一片死白。这和 Blender 的 Filmic/AgX 色彩管理**不是同一条曲线**，所以亮度只能做到「接近」，需要对照测试。
- 没有阴影：灯光会穿过物体照到后面。

## 4. 和 Blender 的对比

| 项目 | PolyView 现在 | Blender Workbench（实体） | Blender Eevee（材质预览/渲染） | Blender Cycles |
| --- | --- | --- | --- | --- |
| 原理 | 光栅化（D3D11） | 光栅化 | 光栅化（+ 屏幕空间技巧） | **路径追踪**（模拟光线多次反弹），原理不同 |
| 实体式光照 | 有：相机主光 + 半球环境 | Studio 灯光（MatCap/Studio） | — | — |
| 场景灯光 | Point/Sun/Spot/Area，最多 16 盏 | 不用 | 有，数量多 | 有，物理正确 |
| 漫反射/高光 | Lambert + 固定 Blinn-Phong | 简化 | **PBR**（Principled BSDF：金属度、粗糙度） | 完整 BSDF |
| 基础颜色贴图 | 有 | 可选 | 有 | 有 |
| 法线/粗糙度/金属度贴图 | **没有** | — | 有 | 有 |
| 阴影 | **没有** | 可选 | 有（阴影贴图） | 有（天然） |
| 环境光遮蔽 AO | **没有** | 可选 Cavity/AO | 有 | 有（天然） |
| 屏幕空间反射 SSR / 透明折射 | **没有** | — | 有 | 有（天然） |
| HDRI 环境贴图 | **没有**，只有纯色 World | Studio HDRI | 有 | 有 |
| 面光 | 点光近似 | — | 真实面光 | 真实面光 |
| 抗锯齿 | **没有**（`SampleDescription(1,0)`） | 有 | 有 | 有（多采样） |
| 色彩管理 | `1-exp(-x)` | Filmic/AgX | Filmic/AgX | Filmic/AgX |
| 速度 | 实时 | 实时 | 实时 | 秒到分钟一张 |

结论：我们的「渲染」模式相当于一个**没有阴影、没有 PBR 的简化版 Eevee**。想往 Eevee 靠，优先顺序建议：抗锯齿 → PBR 材质（读 glTF 的金属度/粗糙度）→ 阴影贴图 → HDRI 环境光。做 Cycles 那种路径追踪工作量完全是另一个量级，不建议。

## 5. 内存与负载

### 5.1 数据格式（来自代码）

| 数据 | 格式 | 大小 |
| --- | --- | --- |
| 顶点 `Vertex` | Position float3 + Normal float3 + TexCoord float2 + Color RGBA8 | **36 字节** |
| 索引 | `R32_UInt` | 4 字节，每三角形 **12 字节** |
| 贴图 | `B8G8R8A8_UNorm`，**MipLevels = 1**（没有 mipmap），不压缩 | 宽 × 高 × 4 字节 |
| 颜色缓冲 | `B8G8R8A8_UNorm`（共享给 D3D9） | 宽 × 高 × 4 |
| 深度缓冲 | `D24_UNorm_S8_UInt` | 宽 × 高 × 4 |
| 描边遮罩 | `R8_UNorm` | 宽 × 高 × 1 |
| 每帧常量 `FrameConstants` | 3 个矩阵 + 2 个 float3 + 3 个 float | 224 字节 |
| 灯光常量 | 32 + 16 × 64 | 1056 字节 |
| 灯光图标缓冲 | 65536 顶点 × 36 | 约 2.4 MB（固定） |

### 5.2 GPU 显存（推算）

**模型**：`显存 ≈ 顶点数 × 36 + 三角形数 × 12`

- 100 万三角形的 **STL**：STL 每个三角形 3 个独立顶点 → 300 万顶点 × 36 = 108 MB，索引 12 MB，合计 **约 120 MB**。
- 100 万三角形、顶点共享的 glTF/OBJ（经 Assimp `JoinIdenticalVertices`，一般顶点数约为三角形数的 0.5～1 倍）：假设 60 万顶点 × 36 ≈ 22 MB + 12 MB ≈ **34 MB**。实际顶点数看文件，状态栏有显示。
- 500 万三角形 STL：1500 万 × 36 ≈ 540 MB + 60 MB（与 docs/04 一致）。

**画面缓冲**：`宽 × 高 × (4 + 4 + 1) = 宽 × 高 × 9 字节`

- 1920×1080：2,073,600 × 9 ≈ **18.7 MB**。
- 3840×2160（4K 或 1080p 在 200% 缩放下的大窗口）：≈ **74.6 MB**。
- D3D9 那张纹理是**同一块显存**（共享句柄），不额外占；WPF 合成桌面时可能再有自己的一份（未实测）。

**贴图**：`宽 × 高 × 4`，没有 mipmap、没有压缩

- 2048×2048：16.8 MB；4096×4096：67 MB。一个带 5 张 4K 贴图的模型 ≈ 335 MB，比网格本身还大。

**例子**：1920×1080 视口 + 100 万三角形 STL + 1 张 2K 贴图 ≈ 120 + 18.7 + 16.8 + 2.4 ≈ **约 158 MB 显存**（推算）。

### 5.3 CPU 内存

- 导入后 `MeshData`（顶点数组、索引数组、贴图像素 `Bgra`）**上传到显卡后仍留在内存**，因为射线拾取（`Picking.cs`，逐三角形检测）和工程文件、大纲都要用。所以 CPU 端约等于再来一份上面的网格 + 贴图大小。
- 导入过程里 `List` 扩容和 `ToArray()` 会让峰值短暂翻倍。
- 实测（docs/04 §5）：空程序约 150 MB 私有内存；100 万三角形 STL 615 MB；500 万三角形 STL 1940 MB。
- 核显（如 Iris Xe）的「显存」本身就是系统内存，所以上面 GPU 那份也算在内存里。

### 5.4 CPU / GPU 负载

- **不动的时候**：`_dirty` 为 false，回调立刻返回，**GPU 接近 0**，CPU 只有 WPF 每帧一次很轻的回调。
- **转视角时**：每帧都画；GPU 时间主要和**三角形数**、**像素数**成正比。实测 Iris Xe：100 万三角形约 4～5 ms/帧，500 万约 18.6 ms/帧（降到 48 FPS）。
- 帧率上限是显示器刷新率（60 Hz 屏就是 60），GPU 闲下来的时间不会浪费在多画帧上。
- 灯光：渲染模式下每个像素要循环所有灯（最多 16），灯越多、窗口越大越慢，但比三角形数的影响小。
- 描边：有选中时，全屏每个像素读 25 次遮罩，1080p 约 5200 万次读取，现代显卡上很便宜，4K 时是 4 倍。

## 6. 现在已经做的优化和潜在风险

**已经做的**

- 按需渲染，不动不画。
- 物体移动/旋转/缩放只改世界矩阵，**不重建顶点缓冲**（`SetWorld`）。
- 一个物体只绑定一次顶点/索引缓冲，按材质分段画；同一高亮状态的连续段不重写常量。
- 渲染循环里用预分配的槽数组和 `for` 循环，常量直接写进映射内存（不经过 `Marshal.StructureToPtr` 装箱），**每帧不产生托管垃圾**。
- 手柄顶点缓冲启动时一次生成；网格只在场景尺度变化时重建。
- 拾取先用包围盒粗筛再逐三角形检测。
- 渲染出错不会让程序崩溃：异常写进 `crash.log`，状态栏显示。
- 改窗口大小时旧的颜色/深度/遮罩纹理和 D3D9 共享纹理都先 `Dispose` 再重建；关闭时 `SceneRenderer.Dispose` 和 `GpuObject.Dispose` 释放所有缓冲、贴图、着色器和设备。

**风险**

- **双份内存**：CPU 和 GPU 各存一份网格和贴图，大模型时内存翻倍。
- **32 位索引 + 36 字节顶点**，没有压缩。
- **没有 mipmap**：贴图远看会闪烁（摩尔纹），而且大贴图缩小时采样更费带宽。
- **单个大缓冲**：一个对象一个顶点缓冲，超大模型可能 `CreateBuffer` 失败（D3D11 只保证至少 128 MB；docs/04 也提到）。
- **拾取是逐三角形**：几百万三角形时点选会卡（没有 BVH，docs/08 列为待借鉴）。
- **删除/替换对象**时要确认对应的 `GpuObject` 被 `Dispose`（代码里有，但多人改代码后建议用诊断工具复查显存是否回落）。
- 着色器运行时编译，依赖系统里的 `d3dcompiler_47.dll`，启动多花一点时间。

## 7. 建议的后续优化与怎么测

| 优化 | 效果 | 难度 |
| --- | --- | --- |
| STL 导入时合并相同顶点（建索引） | STL 顶点数约降到 1/6～1/2，显存和内存都大幅下降 | 低 |
| 顶点数 < 65536 时用 16 位索引（`R16_UInt`） | 小模型索引减半 | 低 |
| 顶点压缩（法线/UV 用 16 位） | 36 → 约 20 字节/顶点（docs/04，未实测） | 中 |
| 贴图生成 mipmap | 远处不闪，采样更快，显存多 1/3 | 低 |
| 贴图压缩 BC1/BC3/BC7 | 显存降到 1/4～1/8 | 中 |
| 上传后释放 CPU 端贴图像素（工程文件改为读原文件） | 省一份贴图内存 | 中 |
| 视锥剔除（看不见的对象/部件不画） | 多对象场景提速 | 低 |
| BVH 加速拾取 | 大模型点选不卡 | 中 |
| LOD（远处用简化网格） | 超大场景提速 | 高 |
| 实例化（同一网格多次出现只存一份） | 重复物体多时省显存 | 中 |
| MSAA 抗锯齿 | 画质（会增加缓冲大小：4× MSAA 颜色+深度约 4 倍） | 低 |

**怎么测**

- **任务管理器** →「性能」→ GPU：看「专用 / 共享 GPU 内存」；「详细信息」页可加「专用 GPU 内存」列看 PolyView 自己占多少。
- **Visual Studio 诊断工具**（调试时 Alt+F2 / 「性能探查器」）：看 CPU 使用率、托管内存、GC 次数；转视角时 GC 不应增加。
- **PIX for Windows** 或 **RenderDoc**：抓一帧，能看到每个 Draw 调用、每个缓冲/纹理的大小和 GPU 耗时，用来核对本文的推算。
- 程序自带 `--bench`（docs/04 §5）：自动转相机，输出 FPS、GPU ms/帧、工作集和私有内存，适合改完优化后对比。
