## 结论

整个项目用 C#。界面用 WPF，渲染用 Direct3D 11，画面通过 `D3DImage` 嵌进 WPF。

WPF 负责窗口、停靠、属性、文件和业务操作。渲染程序负责网格、场景、相机、拾取和 GPU 绘制。像素在 HLSL 里算。界面只保存对象 id，不保存顶点缓冲。

这不是把 Blender 用 C# 重写一遍。第一期只做「能打开模型、能转能看、能选中」。雕刻、程序化建模、关键帧动画、几何节点、离线路径追踪留到后面单独立项。

## 画面怎么嵌进 WPF

用 `D3DImage`，不用 `HwndHost`。

`HwndHost` 是一块盖在 WPF 上的原生窗口。视口上叠不了半透明工具条、视图立方、圆角和阴影，菜单和弹窗也要绕开这块区域。界面要做得好看，这个限制会一直在。

`D3DImage` 在 WPF 视觉树里就是一张图。控件可以叠在视口上，弹窗由 WPF 正常排，DPI 布局也由 WPF 算。渲染结果按物理像素出图：背面缓冲的宽高 = 布局尺寸 × DPI 缩放。100% 和 150% 都要按这个尺寸重建纹理，否则会糊。

WPF 的 `D3DImage.SetBackBuffer` 要的是一块 D3D9 表面。着色仍然全在 D3D11 里完成，D3D9Ex 只做搭桥：

1. D3D11 设备创建时带上 `BGRA` 支持。
2. 颜色画进一张带共享标志的 D3D11 纹理。
3. 用共享句柄在 D3D9Ex 上打开同一张纹理，取出表面交给 `D3DImage`。
4. WPF 合成前在界面线程 `Lock`、`AddDirtyRect`、`Unlock`。

D3D11 立即上下文不是线程安全的。绘制留在渲染线程，界面线程只做上面这一下锁定。两边用同一把锁，设备上打开多线程保护。窗口缩放时先停画，重建共享纹理，再在界面线程重新 `SetBackBuffer`。缩放事件要防抖，拖停靠条时不能每动一个像素就重建一次。

这一步比自己翻交换链多一次显存共享，查看器这个帧率下够用。第 0 阶段就要把纯色、缩放、150% DPI、视口上的弹窗和关闭释放一起验收。

## 为什么可以全部用 C#

顶点进了显存之后，垃圾回收碰不到那块内存。画面卡顿来自两件事：界面线程被加载堵住，以及渲染循环在托管堆上不断分配。把这两件事守住，C# 可以稳定跑 60 帧。

因此从第 0 阶段就执行这些规则：

- 大文件在后台线程流式读取。顶点放进 `ArrayPool` 或 `NativeMemory`，上传到显存后立刻还掉这块内存。
- SharpGLTF 会先建一棵很大的对象图。网格提取完就丢掉这个文档，不把它留在场景里。
- 渲染循环每帧零分配。矩阵用 `struct`。循环里不用 LINQ、闭包和字符串拼接。帧时间用复用的缓冲区显示。
- 显存、纹理、着色器和共享表面都实现 `IDisposable`。关闭模型时显式释放，不等待垃圾回收。
- 纹理压成 GPU 格式，或把长边限制在 2048。场景树用虚拟化列表。
- 模型库里的 GLB 约有 4539 个。它们是逐个打开的压力样例，不是一次性读进内存的场景。
- 每个阶段用 `dotnet-counters` 或 Visual Studio 诊断工具连续打开、关闭模型 20 次，托管内存和工作集要回到基线。

窄边界仍然保留，只是两边都是 C#，不再做 P/Invoke。`PolyView.App` 不碰顶点缓冲，`PolyView.Core` 不引用 WPF。对象用整数 id。加载失败写成一条状态文字，不从渲染循环里往界面抛异常。

核心操作保持这一组：

- 创建 / 销毁视口
- 按像素尺寸重建背面缓冲
- 加载网格，返回对象 id
- 框选全部、环绕、平移、缩放
- 拾取，返回对象 id
- 读取名称、顶点数、面数、包围盒

以后若真要换 C++ 内核，换的是 `PolyView.Core` 里面的实现，界面仍然只认这些 id。

## 阶段

### 第 0 阶段：视口和主题能跑

- 建好解决方案。主窗口用 WPF UI 的深色主题，三栏先用网格：场景树、视口、属性。
- `D3DImage` 清出纯色。拖动窗口时跟着变，150% 缩放下不糊。
- 视口上方能压一个半透明小条和一个弹窗，位置跟着窗口走。
- 关掉程序时设备、共享表面和进程都退出。

停靠条在纯色视口的缩放验收通过后再接 AvalonDock。样式对齐 WPF UI，避免默认蓝色停靠和深色主题各说各的。

验收：连续开关十次，无残留进程。诊断工具里句柄和托管内存没有明显爬升。

### 第 1 阶段：能看一个网格

- 自己的解析器读取一个 OBJ 或 STL，画成带方向光的实体。
- 鼠标左键旋转、中键平移、滚轮缩放，双击或按钮回到全景。
- 显示帧时间和三角形数量。

验收：十万到五十万三角形可以稳定转起来。加载在后台进行，界面不出现「无响应」。连续开关 20 次后内存回到基线。

### 第 2 阶段：场景和选择

- 一次打开多个文件，虚拟化场景树列出对象。
- 点击视口选中对象，属性栏显示名称、顶点、面、包围盒。
- 线框开关、网格开关、重置视角。

验收：选中状态和场景树一致。点空白处取消选择。

### 第 3 阶段：格式和手感

- 用 SharpGLTF 读 glTF / GLB 的网格、基础颜色和法线。读完即释放它的文档对象。
- 视口上叠加坐标轴或视图立方。这一层是 WPF 控件，盖在 `D3DImage` 上。
- 记住上次打开目录。大文件给出读取进度。
- 从现有 GLB 库里抽大文件逐个打开，不一次加载整库。

验收：同一批样例在 100%、150% 下都清晰，视口比例正确。连续开关 20 次，内存回到基线。

## 和现有 WPF 程序的关系

现有激光控制程序继续用 WPF 做业务界面。三维预览要嵌进去时，嵌同一块视口控件和同一份 `PolyView.Core`，不在业务工程里再写一套绘制。

业务程序只调用「加载路径、设置相机、取选中对象」。渲染库不依赖激光控制器、脚本编辑器或机台配置。

## 风险

- `Lock` / `Unlock` 在界面线程。绘制若也放在界面线程，加载大模型时界面会假死。加载和绘制分开，界面线程只提交脏矩形。
- 缩放、DPI 变化和停靠拖拽都会重建共享纹理。重建期间要停画，否则会使用已释放的表面。
- SharpGLTF 的对象图是导入阶段的内存高峰。高峰过去后若文档还被场景引用，关模型也回不到基线。
- 第一期只维护 D3D11 这一套后端。
- 模型若连动画、蒙皮和完整 PBR 一起读进来，范围会滑向数字内容创作软件。
- GPU 资源交给垃圾回收，关闭模型后显存仍会涨。释放写在 `Dispose` 里，并用 20 次开关来验收。

## 第一期完成的样子

打开程序，拖进一个 STL、OBJ 或 GLB，模型出现在视口中。鼠标可以转、移、缩放。视口上能看到坐标轴，弹窗不会被视口吃掉。点一下模型，右侧出现面数和尺寸。线框可以开关。关掉再打开一批模型，内存回到基线，进程退出干净。

做到这里，再决定要不要往动画、测量或更重的渲染走。
