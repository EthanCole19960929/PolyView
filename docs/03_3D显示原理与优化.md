# PolyView：3D 模型是怎么显示出来的、怎么优化、能显示多大（草稿，数字为估算）

日期：2026-10-23　作者：小U

> 说明：本文按《[01_开发计划说明.md](01_开发计划说明.md)》的架构来写。文中的容量数字是按显存和带宽**估算**的，还没有在你的电脑上实测。第 1 阶段做压力测试时，要用实测数字替换本文的估算。

## 一、一句话讲清楚

文件 → 后台线程解析成顶点和索引 → 上传到显卡（显存）→ 每帧由 D3D11 用着色器画进一张共享纹理 → WPF 的 `D3DImage` 把这张纹理当成一张图显示在窗口里。

```mermaid
flowchart LR
  A[OBJ / STL / GLB / FBX 文件] -->|后台线程解析| B[顶点数组 + 索引数组]
  B -->|上传一次| C[显存：顶点缓冲 / 索引缓冲]
  C -->|每帧绘制| D[D3D11 共享纹理]
  D -->|D3D9Ex 共享句柄| E[D3DImage]
  E --> F[WPF 窗口]
```

## 二、显示流程，分五步

### 1. 读文件（加载）
- OBJ、STL 用自己的解析器，GLB/glTF 用 SharpGLTF（或者换成 AssimpNet，它一个库就能读 OBJ、STL、FBX、DAE、GLB）。
- 解析结果统一成一种格式：**顶点数组**（位置、法线，以后加 UV）和**索引数组**（每 3 个索引组成一个三角形）。
- 文件里没有法线时，按面自动计算法线，否则光照会发黑。
- 解析在**后台线程**里做，界面线程不等待，所以打开大文件时窗口不会「无响应」。

### 2. 上传到显卡
- 顶点数组和索引数组各建一个 GPU 缓冲（`ID3D11Buffer`），只上传一次。
- 上传完以后立刻释放内存里的那份数组，内存里只留对象 id、名称、顶点数、面数、包围盒。
- 这样垃圾回收碰不到显存里的数据，模型再大也不会造成 GC 卡顿。

### 3. 相机和投影
三个矩阵相乘，决定模型在屏幕上的位置：
- **World（世界矩阵）**：模型自己的位置、旋转、缩放。
- **View（观察矩阵）**：相机在哪、看向哪里。环绕相机以模型包围盒的中心为旋转中心。
- **Projection（投影矩阵）**：透视效果，用 `CreatePerspectiveFieldOfView`，视角约 45°，宽高比 = 背面缓冲的**像素**宽 ÷ 像素高。

注意：`System.Numerics` 的矩阵按行存，HLSL 默认按列读。上传前必须 `Matrix4x4.Transpose`，否则画面会歪斜（之前长方体被拉斜就是这类问题）。

「复位视角」：相机看向包围盒中心，距离 = 包围盒半径 ÷ tan(视角的一半) × 1.2，模型正好填满画面。

### 4. GPU 绘制（着色器）
- **顶点着色器**（HLSL）：把每个顶点乘上 World × View × Projection，算出屏幕位置；法线跟着 World 一起变换。
- **像素着色器**（HLSL）：方向光 + 一点环境光，算每个像素的明暗，保证最暗处也比背景亮。
- 每帧开头清颜色和**深度缓冲**，有深度缓冲前后遮挡才正确。
- 线框模式只是把光栅化状态的填充方式改成 Wireframe，不用另外准备数据。

### 5. 嵌进 WPF
- D3D11 把画面画进一张带共享标志的纹理（BGRA 格式）。
- D3D9Ex 通过共享句柄打开同一张纹理，交给 `D3DImage.SetBackBuffer`。
- 界面线程只做 `Lock` → `AddDirtyRect` → `Unlock`，提交之前 D3D11 要先 `Flush`，避免拿到画到一半的帧。
- 因为 `D3DImage` 在 WPF 里就是一张图，工具条、坐标轴、弹窗都能直接盖在视口上面。
- 纹理按物理像素建：宽高 = 布局尺寸 × DPI 缩放，150% 缩放下才不会糊。

### 6. 点选（拾取）
- 把鼠标位置反投影成一条射线，先和每个对象的包围盒求交，挑出候选对象，再和三角形求交，取最近的那个，返回对象 id。
- 属性栏只拿 id 去查名称、顶点数、面数、包围盒。

## 三、优化是怎么做的

| 问题 | 做法 |
| --- | --- |
| 打开大文件时界面卡死 | 解析放后台线程，界面线程只显示进度 |
| 加载时内存峰值高 | 顶点放进 `ArrayPool` / `NativeMemory`，上传后立刻还回；SharpGLTF / Assimp 的文档对象读完就丢掉 |
| 渲染时 GC 卡顿 | 渲染循环每帧零分配：矩阵用 `struct`，不用 LINQ、闭包、字符串拼接；FPS 文字每 0.5 秒才刷新一次 |
| 关模型后显存不回落 | 所有 GPU 资源实现 `IDisposable`，关模型时显式释放，不等 GC |
| 不需要时也在重画 | 静止时不重画，只在相机移动、窗口缩放、加载新模型时才画（按需渲染），省电也省 GPU |
| 窗口缩放卡顿或崩溃 | 缩放事件防抖；重建共享纹理期间暂停绘制，再重新 `SetBackBuffer` |
| 锁屏或远程桌面切换后黑屏 | 处理 `IsFrontBufferAvailableChanged`，失效时停画，恢复后重建共享表面 |
| 贴图太占显存 | 长边限制在 2048，或压成 GPU 压缩格式（BC1 / BC3 / BC7） |
| 对象太多时场景树卡 | 场景树用虚拟化列表，只创建屏幕上能看到的行 |
| 一个对象几千次绘制调用 | 同一个对象的网格合并成一个缓冲，一次绘制调用画完 |

以后模型更大时可以再加：
- **视锥剔除**：相机看不到的对象不画（用包围盒判断）。
- **LOD**：远处用减面后的版本。
- **点选加速**：给三角形建 BVH 树，几百万面也能瞬间拾取。

## 四、能显示多大的模型（估算）

每个顶点存位置和法线，共 24 字节（加 UV 是 32 字节）；索引用 32 位，每个三角形 12 字节。一个三角形网格的顶点数大约是三角形数的 0.5 到 1 倍，下面按每个顶点 32 字节、顶点数等于三角形数的较坏情况来估：

| 三角形数 | 显存占用（估算） | 预期表现（估算） |
| --- | --- | --- |
| 10 万 | 约 4 MB | 任何显卡都能稳定 60 帧 |
| 50 万（第 1 阶段验收线） | 约 22 MB | 集成显卡也应能 60 帧 |
| 100 万 | 约 44 MB | 独立显卡轻松，集显可能开始掉帧 |
| 1000 万 | 约 440 MB | 中端独显（4 GB 以上）应能流畅旋转 |
| 5000 万以上 | 约 2.2 GB 以上 | 要靠 LOD、剔除或分块加载 |

真正先碰到的限制往往不是显存，而是：
1. **加载时的内存峰值**：Assimp / SharpGLTF 会先建一整棵对象树，峰值大约是文件大小的几倍。所以加载必须在后台、读完立刻释放。
2. **.NET 单个数组的上限**：单个数组最多约 20 亿个元素。上亿面的模型要用 `NativeMemory` 或者分块。
3. **点选速度**：不建 BVH 的话，在几百万面上逐个三角形求交，点一下就会卡一下。

第 1 阶段的验收线是 10 万到 50 万三角形稳定旋转，从上面的估算看余量很大。实测时用 `dotnet-counters` 记下帧率、显存和托管内存，把这一节的估算换成实测数字。

## 五、和 Unity 的对照（方便理解）

| PolyView | Unity 里对应的东西 |
| --- | --- |
| 顶点缓冲 + 索引缓冲 | `Mesh`（vertices + triangles） |
| World / View / Projection 矩阵 | `Transform` / `Camera` 的 worldToCamera / projectionMatrix |
| HLSL 顶点 / 像素着色器 | Shader 里的 vert / frag |
| 深度缓冲 | ZWrite / ZTest |
| 拾取射线 | `Camera.ScreenPointToRay` + `Physics.Raycast` |
| 按需渲染 | 编辑器 Scene 视图静止时不重画 |
